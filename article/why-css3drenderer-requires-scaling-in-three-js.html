Why CSS3DRenderer Requires Scaling in Three.js

When developing hybrid applications with Three.js, developers often notice that CSS3DRenderer does not visually match the coordinate scale of WebGLRenderer out of the box. This article explains why this discrepancy occurs, focusing on the fundamental conflict between CSS pixel units and WebGL world units, the requirement for legible text resolution, and the mathematical mechanics used by the renderer to map 3D camera projections onto CSS 3D transforms.

Pixels Versus Abstract World Units

The primary driver of the scale mismatch is the difference in measurement systems. In standard Three.js scenes rendered via WebGL, units are dimensionless and arbitrary. By industry convention, developers treat 1 unit as 1 meter to work predictably with physics engines, lighting attenuation, and virtual camera optics.

In contrast, CSS3DRenderer targets the Document Object Model (DOM). DOM elements are governed by the CSS box model, which relies on physical screen units—most commonly pixels (px). By default, CSS3DRenderer treats 1 Three.js world unit as 1 CSS pixel. If a WebGL character or prop is built to a scale of 2 units high, placing a standard 200×200-pixel HTML div into the scene causes an extreme disparity: the HTML element evaluates to 200 units tall, appearing 100 times larger than the WebGL geometry.

DOM Resolution and Typography Crispness

The second reason for significant scale adjustments is the way web browsers rasterize text and vector assets. If a developer attempts to align DOM elements directly with WebGL unit values—such as creating an HTML element that is 2px wide to match a 2-unit mesh—the browser will rasterize typography and CSS styles within that tiny pixel budget. The result is unreadable, heavily pixelated content.

To retain sharp text and clean interfaces, elements must be styled with realistic pixel budgets (for example, 400px by 300px) and then scaled down in the 3D scene:

const element = document.createElement('div');
element.style.width = '400px';
element.style.height = '300px';

const objectCSS = new CSS3DObject(element);
// Scale down to fit WebGL scene dimensions
objectCSS.scale.set(0.01, 0.01, 0.01); 
scene.add(objectCSS);

By applying a fractional scale factor (such as 0.01 or 0.001), the DOM element maintains a high internal pixel density while visually conforming to the physical dimensions of the WebGL models around it.

Camera Projection and CSS Perspective

The mathematical bridge between Three.js and the DOM is the CSS matrix3d() transform. To make regular DOM nodes follow a 3D perspective camera, CSS3DRenderer converts the camera’s vertical Field of View (FOV) and viewport height into a CSS perspective value:

\[\text{perspective} = \frac{\text{viewport height}}{2 \times \tan(\text{FOV} / 2)}\]

Because the rendering target is an HTML container measured in screen pixels, the camera's visual frustum is computed in pixel-space distances. WebGL shaders calculate projection matrices in normalized device coordinates (ranging from -1 to 1), whereas CSS relies on continuous screen-space values. Consequently, manual scaling adjustments are essential to synchronize how far or close objects appear when switching between or overlaying both rendering pipelines.

Standardizing the Pipeline

To resolve these scale differences reliably, establish a fixed conversion factor across your project. A common approach is establishing that 1 Three.js unit equals a fixed pixel value (e.g., 100 CSS pixels). Applying this ratio systematically to the size, offset, and scale of all CSS3DObject instances guarantees that DOM-based interfaces integrate seamlessly alongside WebGL meshes.

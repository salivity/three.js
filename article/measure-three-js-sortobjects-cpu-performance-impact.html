Measure Three.js sortObjects CPU Performance Impact

This article details how to accurately isolate and measure the CPU overhead introduced by the WebGLRenderer.sortObjects property when rendering thousands of transparent meshes in Three.js. By understanding why Three.js performs depth sorting for transparent materials and implementing targeted profiling techniques using high-resolution timers and browser developer tools, you can determine whether this setting creates a frame-rate bottleneck in your WebGL application.

Why sortObjects Impacts the CPU

By default, Three.js sets WebGLRenderer.sortObjects to true. While opaque meshes do not require depth sorting due to the GPU depth buffer, transparent objects must be sorted back-to-front relative to the camera to blend colors correctly.

When you have thousands of transparent meshes, Three.js iterates through them and executes a sorting routine (typically O(N log N)) on the CPU on every single frame before sending draw calls to the GPU. This CPU-side sorting can quickly become a significant performance bottleneck, consuming frame budget and lowering overall FPS.

Setting Up an Isolated Test Scene

To measure purely the CPU impact rather than GPU fill-rate limits, reduce GPU load by minimizing draw resolution or using small, simple geometries:

const renderer = new THREE.WebGLRenderer();
renderer.setSize(window.innerWidth, window.innerHeight);
document.body.appendChild(renderer.domElement);

const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(60, window.innerWidth / window.innerHeight, 0.1, 1000);
camera.position.z = 50;

// Create 10,000 transparent meshes
const geometry = new THREE.BoxGeometry(0.5, 0.5, 0.5);
const material = new THREE.MeshBasicMaterial({ transparent: true, opacity: 0.5 });

for (let i = 0; i < 10000; i++) {
  const mesh = new THREE.Mesh(geometry, material);
  mesh.position.set(
    (Math.random() - 0.5) * 100,
    (Math.random() - 0.5) * 100,
    (Math.random() - 0.5) * 100
  );
  scene.add(mesh);
}

Ensure the camera moves slightly on each frame to force dynamic depth changes relative to the view matrix.

Method 1: Programmatic Measurement with performance.now()

The most direct way to measure CPU execution time is to isolate the renderer.render() execution using the High Resolution Time API.

let totalRenderTime = 0;
let frameCount = 0;
const testFrames = 500;

renderer.sortObjects = true; // Toggle between true and false for comparison

function animate() {
  camera.position.x = Math.sin(Date.now() * 0.001) * 50;
  camera.lookAt(scene.position);

  const start = performance.now();
  renderer.render(scene, camera);
  const end = performance.now();

  totalRenderTime += (end - start);
  frameCount++;

  if (frameCount < testFrames) {
    requestAnimationFrame(animate);
  } else {
    console.log(`Average CPU render time: ${(totalRenderTime / testFrames).toFixed(3)} ms`);
  }
}

animate();

Run this benchmark across several hundred frames with renderer.sortObjects = true, record the average millisecond duration, and repeat the test with renderer.sortObjects = false. The difference between the two numbers isolates the CPU cost of the sort operation.

Method 2: Browser DevTools Profiling

To visually inspect where the CPU cycles are being spent:

  1. Open Chrome DevTools (or your browser's equivalent) and navigate to the Performance tab.
  2. Click Record and allow the scene to run for 3 to 5 seconds.
  3. Stop the recording and inspect the Main thread flame chart.
  4. Locate the render call stack.
  5. Look for the Three.js internal render list functions, specifically projectObject and the array sorting routine (renderList.sort() or painterSortStable).

When sortObjects is enabled, the flame chart will show significant block width allocated to sorting arrays of transparent items. Disabling sortObjects removes this execution block entirely from the call tree.

Isolating CPU vs. GPU Bottlenecks

A common pitfall is mistaking GPU overdraw for CPU sorting delay:

  • Overdraw Bound (GPU): Thousands of overlapping transparent surfaces cause extensive fragment shader calculations, raising the GPU frame time.
  • Sorting Bound (CPU): High CPU frame times occur within the JavaScript thread during the render preparation step.

To prevent GPU limitations from masking CPU measurements:

  • Set the canvas size very small (e.g., 100x100) while maintaining the mesh count.
  • Monitor CPU core usage via the Performance tab. If JS frame processing time drops significantly when setting renderer.sortObjects = false, the application is CPU-bound by the object sorter.

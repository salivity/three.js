Optimize Skeleton.update for Crowds in Three.js

Simulating massive crowds in Three.js frequently results in CPU bottlenecks caused by Skeleton.update, which calculates global bone matrices and updates matrix texture buffers for every skinned mesh on the main thread. This article covers practical strategies to eliminate or reduce this CPU cost, including Vertex Animation Textures (VAT), bone matrix update throttling, animation Level of Detail (LOD), frustum-based skeleton culling, and skeleton sharing.

1. Bake Animations into Textures (Vertex Animation Textures / VAT)

The most effective way to eliminate Skeleton.update entirely for large crowds is to bypass Three.js skeletons completely by baking skeletal animations into floating-point textures.

  • How it works: Store the precomputed positions, normals, or bone matrices for each animation frame in a DataTexture.
  • GPU Execution: In a custom vertex shader (or a modified MeshStandardMaterial), sample the current frame from the texture using an animation time uniform and apply transforms directly to vertices.
  • Instancing: Combine this with InstancedMesh to render thousands of characters in a single draw call with zero skeletal CPU overhead. Libraries like three-subdivide or tools like Houdini and Blender can generate VAT assets.

2. Implement Animation Level of Detail (LOD)

Running matrix calculations at 60 FPS for characters far in the background wastes CPU cycles. Throttle how often AnimationMixer.update() and Skeleton.update() execute based on distance from the camera.

  • Near: Update every frame (60 Hz).
  • Medium distance: Update every other frame (30 Hz).
  • Far distance: Update every 4 to 6 frames (10–15 Hz).

Track elapsed time manually per character tier and only invoke the mixer's update method when the interval has elapsed.

3. Frustum Cull Skeleton Matrix Updates

By default, Three.js frustum culling determines whether a mesh is rendered by the GPU, but it does not automatically stop AnimationMixer or Skeleton from updating on the CPU.

Check if a character's bounding sphere intersects the camera frustum:

const frustum = new THREE.Frustum();
const projScreenMatrix = new THREE.Matrix4();

// Inside your render loop
projScreenMatrix.multiplyMatrices(camera.projectionMatrix, camera.matrixWorldInverse);
frustum.setFromProjectionMatrix(projScreenMatrix);

if (frustum.intersectsSphere(characterBoundingSphere)) {
    mixer.update(delta);
}

If the character is off-screen, completely skip both mixer.update(delta) and manual skeleton recalculations.

4. Share Skeletons Across Synchronized Characters

If multiple crowd members share the same mesh topology and perform identical animations simultaneously (such as marching soldiers or cheering stadium crowds), bind multiple SkinnedMesh instances to a single Skeleton and AnimationMixer.

const sharedSkeleton = leaderMesh.skeleton;
followerMesh.bind(sharedSkeleton, followerMesh.bindMatrix);

This ensures the bone hierarchy is evaluated only once per frame on the CPU, while rendering across multiple mesh instances.

5. Minimize Rig Complexity

The execution time of Skeleton.update scales linearly with the total number of bones. Hero rigs often contain 60 to 100+ bones (including facial rigs, twist bones, and cloth helpers).

  • Strip crowd models down to the absolute minimum required for recognizable motion (typically 18–24 bones).
  • Remove non-deforming helper bones and bake constraints directly into primary deforming bones during export.

Using WebGL1 and WebGL2 Directives in Three.js

This article explains how to properly handle WebGL1 and WebGL2 preprocessor directives within raw GLSL shader strings in Three.js. Because GLSL requires version specifications to appear on the first line of code, managing WebGL compatibility requires understanding how the preprocessor interacts with Three.js compilation pipelines. You will learn the restrictions of the #version directive, how to pass context capabilities via material definitions, and how to conditionally compile GLSL blocks across both contexts.

The Preprocessor Limitation with #version

In GLSL, the #version 300 es directive declares that the shader should be compiled as WebGL2. A strict rule of the GLSL specification is that #version must be the absolute first token in the shader, preceded only by whitespace or comments.

Because of this rule, you cannot wrap #version inside a preprocessor conditional like this:

// INVALID GLSL:
#ifdef WEBGL2
#version 300 es
#endif

Attempting this causes a shader compilation failure. To write a raw shader compatible with both WebGL1 and WebGL2, you must choose one of two approaches:

  1. Dynamic string generation in JavaScript to inject the #version tag before shader compilation.
  2. GLSL 1.00 backward compatibility, compiling the shader as GLSL 1.00 (which WebGL2 natively supports) while using preprocessor conditionals for context-specific behavior.

Approach 1: Dynamic Version Injection with RawShaderMaterial

When using modern Three.js, you can specify glslVersion: THREE.GLSL3 on a RawShaderMaterial. When this property is set, Three.js prepends #version 300 es internally.

To support both environments dynamically using template literals, check renderer.capabilities.isWebGL2 when configuring your material:

const isWebGL2 = renderer.capabilities.isWebGL2;

const material = new THREE.RawShaderMaterial({
  glslVersion: isWebGL2 ? THREE.GLSL3 : null,
  defines: {
    IS_WEBGL2: isWebGL2 ? '' : undefined
  },
  vertexShader: `
    ${isWebGL2 ? '' : '#define attribute in\n#define varying out'}
    // Common shader logic
  `,
  fragmentShader: getFragmentShader(isWebGL2)
});

Approach 2: Using Defines in GLSL 1.00 Compatibility Mode

If you omit the #version 300 es directive entirely, WebGL2 treats the shader as GLSL 1.00. This enables writing a single raw string without JS-level string splitting, branching context features through #ifdef.

1. Pass Capabilities via defines

Inject a preprocessor flag using renderer.capabilities.isWebGL2:

const rawMaterial = new THREE.RawShaderMaterial({
  defines: {
    USE_WEBGL2: renderer.capabilities.isWebGL2 ? '1' : '0'
  },
  vertexShader: rawVertexShader,
  fragmentShader: rawFragmentShader
});

2. Implement Directives in the Fragment Shader

Inside your raw GLSL string, branch syntax differences such as derivatives, texture lookups, or output variables:

precision highp float;

#if USE_WEBGL2 == 1
  // WebGL 2 behavior
  out vec4 fragColor;
  #define gl_FragColor fragColor
  #define texture2D texture
#else
  // WebGL 1 behavior
  #extension GL_OES_standard_derivatives : enable
#endif

uniform sampler2D uTexture;
varying vec2 vUv;

void main() {
  #if USE_WEBGL2 == 1
    vec4 color = texture(uTexture, vUv);
  #else
    vec4 color = texture2D(uTexture, vUv);
  #endif

  gl_FragColor = color;
}

Key Syntax Differences to Handle via Directives

When writing raw shaders to run across both targets, common syntax differences must be accounted for using preprocessor blocks:

  • Varyings and Attributes: GLSL 1.00 uses attribute and varying. GLSL 3.00 ES uses in and out.
  • Fragment Output: GLSL 1.00 writes to the built-in gl_FragColor. GLSL 3.00 ES requires defining a custom output variable (out vec4 fragColor;).
  • Texture Sampling: GLSL 1.00 uses texture2D, textureCube, etc. GLSL 3.00 ES unifies these into overloaded texture calls.
  • Standard Extensions: Features like derivatives (dFdx, dFdy) and draw buffers require #extension declarations in WebGL1, but are built-in core functionality in WebGL2 without extensions.

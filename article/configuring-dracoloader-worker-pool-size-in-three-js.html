Configuring DRACOLoader Worker Pool Size in Three.js

Optimizing 3D asset loading in Three.js requires balancing WebAssembly decoding speed against device memory consumption when using Draco compression. This guide explains how DRACOLoader manages Web Workers, how to configure the worker pool using setWorkerLimit(), and how to determine the optimal worker count dynamically based on the user's hardware to prevent browser tab crashes and reduce load times.

Understanding the Speed vs. Memory Trade-Off

DRACOLoader offloads geometry decompression from the main UI thread to background Web Workers running a compiled WebAssembly (or JavaScript fallback) decoder.

  • High Worker Pool (Speed-focused): Spawning multiple workers allows parallel decoding of distinct geometries. This drastically reduces total scene loading time when downloading glTF models with dozens or hundreds of individual compressed meshes. However, each worker allocates its own instance of the WebAssembly module and dedicated memory buffers, which can quickly consume hundreds of megabytes of RAM.
  • Low Worker Pool (Memory-focused): Restricting workers reduces peak memory overhead, eliminating Out-Of-Memory (OOM) browser crashes on low-end and mobile devices. The trade-off is that decoding tasks are queued sequentially, increasing overall load duration on multi-core systems.

Setting the Worker Limit

By default, Three.js sets the worker limit to 4. You can override this behavior using the setWorkerLimit() method on your DRACOLoader instance before passing it to GLTFLoader:

import { DRACOLoader } from 'three/addons/loaders/DRACOLoader.js';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';

const dracoLoader = new DRACOLoader();
dracoLoader.setDecoderPath('/draco/');

// Manually restrict the maximum number of concurrent workers
dracoLoader.setWorkerLimit(2);

const gltfLoader = new GLTFLoader();
gltfLoader.setDRACOLoader(dracoLoader);

Determining the Optimal Pool Size Dynamically

Hardcoding a single number across all platforms leads to either sub-optimal desktop performance or mobile crashes. The ideal approach dynamically calculates the worker pool using navigator.hardwareConcurrency alongside platform capability checks:

function getOptimalDracoWorkerLimit() {
  const logicalCores = navigator.hardwareConcurrency || 4;
  const isMobile = /Mobi|Android|iPhone|iPad/i.test(navigator.userAgent);

  if (isMobile) {
    // Mobile: Prioritize memory safety. 
    // Cap strictly at 1 or 2 workers to avoid mobile OS memory terminations.
    return Math.min(logicalCores, 2);
  }

  // Desktop: Leave at least one core free for the main UI/render thread.
  // Cap at 4 to avoid diminishing returns and excessive WASM memory allocation.
  return Math.min(Math.max(logicalCores - 1, 1), 4);
}

dracoLoader.setWorkerLimit(getOptimalDracoWorkerLimit());

Memory Management Best Practices

  1. Dispose When Finished: Web Workers remain active in memory waiting for new tasks once spawned. When your scene is fully loaded and no further Draco assets will be requested, call dracoLoader.dispose() to terminate the worker pool and release WebAssembly memory immediately.
  2. Batch Small Geometries: Having a large worker pool to decode hundreds of tiny meshes introduces scheduling and message-passing overhead that can outweigh parallel decoding benefits. Where possible, merge static geometries before Draco compression to allow a smaller worker pool to process larger, contiguous data blocks more efficiently.
  3. Avoid Dynamic Over-Allocation: Draco WebAssembly modules generally operate best when memory is pre-allocated. Spawning more than 4 workers rarely yields a linear performance gain due to memory transfer serialization between the worker threads and the main Three.js buffer attributes.

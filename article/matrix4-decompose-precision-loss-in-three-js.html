Matrix4 Decompose Precision Loss in Three.js

Repeatedly alternating between Matrix4.decompose and Matrix4.compose in a recursive Three.js animation loop causes cumulative precision loss that manifests as visual artifacts, unintended scaling, and rotational drift. When a transformation matrix is repeatedly extracted into separate position, quaternion, and scale vectors and then reconstructed, the floating-point calculations within the extraction algorithms introduce tiny numerical errors. Over hundreds or thousands of frames, these minuscule inaccuracies compound, gradually degrading the mathematical integrity of the transformation matrix.

The Underlying Floating-Point Limits

JavaScript calculates numbers using 64-bit double-precision floating-point format (IEEE 754). Although 64-bit floats offer significant precision, mathematical operations involving square roots, divisions, and trigonometric calculations cannot always be represented exactly in binary.

In a recursive loop where a matrix is updated based on its own previous state (e.g., \(M_{t} = \text{compose}(\text{decompose}(M_{t-1}))\)), errors are not cleared between frames. Instead, each frame uses a slightly corrupted base state to calculate the next, turning minor rounding inaccuracies into a noticeable feedback loop.

How decompose Introduces Numerical Drift

The Matrix4.decompose(position, quaternion, scale) method performs several operations that are vulnerable to precision degradation:

  1. Length Calculations for Scale Extraction: To extract scale, Three.js calculates the Euclidean norm (length) of the matrix's column or row vectors using Math.hypot or Math.sqrt(x*x + y*y + z*z). The square root of a sum of squares rarely yields an exact floating-point representation.
  2. Matrix Normalization for Rotation: Once the scale vector is calculated, the rotation components are isolated by dividing the matrix elements by their corresponding scale factors. If the extracted scale is slightly off due to square root rounding, dividing by it introduces an error into the directional vectors.
  3. Quaternion Extraction: Converting the normalized matrix basis into a quaternion requires additional square roots and division operations depending on the matrix trace. Even small errors in the basis vectors disrupt the orthogonality of the rotation component, leading to a quaternion that is no longer strictly normalized (\(||q|| \neq 1\)).

How compose Amplifies the Error

When Matrix4.compose(position, quaternion, scale) reconstructs the transformation matrix, it multiplies the rotation matrix generated from the quaternion by the scale vector and sets the translation column.

If the input quaternion has drifted from unit length, or the scale has drifted from its intended values:

  • Scale Inflation or Deflation: An extracted scale of 1.0000000000000002 applied iteratively will compound exponentially, causing the 3D model to shrink or expand over time.
  • Shearing and Orthogonality Loss: Although compose forces a rigid rotation-scale structure, using corrupted basis values continuously distorts the intended transformation, causing visual jitter or drift.

The Impact in a Recursive Animation Loop

In a standard animation loop running at 60 or 120 FPS, the loop executes thousands of times within minutes:

function animate() {
    requestAnimationFrame(animate);

    // Recursive state retrieval
    matrix.decompose(position, quaternion, scale);

    // Apply incremental transformation
    quaternion.multiply(deltaRotation);

    // Recompose back into the same matrix
    matrix.compose(position, quaternion, scale);
}

Because matrix serves as both the source and destination of the state, there is no immutable "ground truth." The accumulated floating-point drift directly alters the transformation parameters for the subsequent frame.

Mitigating Precision Loss

To avoid precision loss in Three.js animations, eliminate recursive matrix decomposition:

  • Maintain Independent State (Ground Truth): Store the object's canonical transformation as separate persistent properties (such as distinct Vector3 instances for position and scale, and a Quaternion for rotation). Modify these variables directly and generate the Matrix4 from them in a one-way pipeline.
  • Use Object3D Hierarchy: Rely on standard Object3D properties (position, quaternion, scale). Three.js automatically manages matrixWorld updates in a unidirectional manner from these source values, eliminating iterative decomposition.
  • Explicit Normalization: If recursive quaternion multiplication is unavoidable, explicitly call quaternion.normalize() on every iteration to keep the rotation unit-length and prevent drift from affecting scale and rotation.

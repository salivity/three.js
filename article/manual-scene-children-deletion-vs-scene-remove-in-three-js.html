Manual scene.children Deletion vs scene.remove in Three.js

Manually removing an object from scene.children instead of using scene.remove() disrupts internal Three.js state tracking, potentially breaks the render loop, and leaves dangling references in CPU memory. While manually splicing the array prevents the object from being drawn, it bypasses the critical step of clearing the object's parent property and fails to emit lifecycle events. Furthermore, neither approach frees GPU memory, meaning materials, textures, and geometries remain in VRAM unless explicitly disposed.

How scene.remove() Works Internally

To understand the problems with manual deletion, consider what scene.remove(object) actually does under the hood:

  1. Locates the object's index within scene.children.
  2. Splices the array to remove the object.
  3. Sets object.parent = null.
  4. Dispatches the removed event to the target object and its descendants.

Rendering Consequences

The impact on the rendering pipeline depends entirely on how the manual deletion is performed:

  • Using the delete operator (delete scene.children[index]): This is fatal to the render loop. The delete operator leaves an empty slot (undefined) in the array rather than shifting elements. During the next frame, when the renderer attempts to traverse scene.children, it encounters undefined and throws a TypeError: Cannot read properties of undefined when trying to access layers or visibility flags, crashing your entire render loop.
  • Using Array.prototype.splice(): If you manually call scene.children.splice(index, 1), the object is successfully eliminated from the array. Because the WebGLRenderer iterates directly over active array elements to build the render list, the object will immediately stop rendering. However, because object.parent is never set to null, any custom logic or third-party libraries checking scene hierarchy via .parent will falsely detect that the object is still part of the active scene graph.

CPU Memory Consequences

Manually removing an element from the array without resetting its parent reference creates an asymmetric relationship: the scene no longer knows about the child, but the child still points to the scene.

Modern JavaScript garbage collectors handle circular references effectively, so if all external references to the removed object are dropped, CPU memory will eventually be reclaimed. However, if your application holds onto the removed object, the remaining object.parent pointer will prevent the scene (and everything attached to it) from being eligible for garbage collection, leading to severe CPU memory leaks.

Additionally, custom event systems or systems relying on the removed event will not be notified, leaving orphaned listeners intact.

GPU Memory (VRAM) is Unaffected

A common misconception is that scene.remove() manages GPU resource cleanup. In reality, neither scene.remove() nor manual array modification affects WebGL memory:

  • Geometries, materials, and textures reside in GPU buffers managed directly by the WebGL context.
  • Removing an object from the scene hierarchy solely stops CPU-side tracking and WebGL render list generation.
  • To completely free memory on the GPU, you must manually traverse the object and invoke .dispose() on its geometry, materials, and associated textures.

Summary

Directly modifying scene.children provides no performance benefits and introduces hierarchy synchronization bugs or runtime crashes. Always use scene.remove(object) to maintain correct scene graph relationships, and chain .dispose() calls on underlying assets when the object is no longer needed.

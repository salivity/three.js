Force Three.js Shader Recompile with material.version

In Three.js, shaders are compiled once and cached by the WebGL renderer to optimize rendering performance. However, when you dynamically inject GLSL code, modify defines, or alter shaders using callbacks like onBeforeCompile, Three.js might reuse the cached program instead of applying your updates. This article explains how to invalidate the shader program cache and force an immediate shader recompilation by incrementing the material.version property.

Why Three.js Caches Shaders

When rendering a scene, THREE.WebGLRenderer checks whether a material's shader program has already been built. If the material configuration matches an existing program in the internal program cache, Three.js avoids the costly operation of recompiling GLSL code. While this is optimal for performance, it prevents the renderer from recognizing manual or runtime alterations made to raw shader strings or custom defines unless explicitly told that the material has changed.

Understanding material.version

Every instance of THREE.Material maintains an internal integer property: material.version.

Under normal circumstances, setting material.needsUpdate = true acts as a setter that automatically increments material.version by 1. However, directly incrementing material.version provides a clean, programmatic way to flag a material as "dirty" across custom rendering pipelines, extensions, or shader caching layers.

When the renderer encounters a material whose version does not match the version associated with the currently cached WebGL program, it treats the material as outdated, flushes the cached state for that object, and compiles a fresh WebGL shader program.

How to Increment material.version

To force recompilation, increment the property directly on your material instance:

// Force the material to recompile its shader
material.version++;

Example: Dynamic Updates with onBeforeCompile

A common scenario where shader recompilation is necessary involves altering the material via onBeforeCompile. If you alter properties inside or around this hook after the initial render, increment material.version to ensure your GLSL changes take effect:

import * as THREE from 'three';

const material = new THREE.MeshStandardMaterial({ color: 0x00ff00 });

// Customize the shader before compilation
material.onBeforeCompile = (shader) => {
  shader.fragmentShader = shader.fragmentShader.replace(
    '#include <dithering_fragment>',
    `
    #include <dithering_fragment>
    gl_FragColor = vec4(1.0, 0.0, 0.0, 1.0); // Override output color
    `
  );
};

// Invalidate existing compiled programs and force recompilation
material.version++;

Example: Modifying Shader Defines

If you conditionally toggle #define directives in your shaders during runtime, incrementing version ensures the preprocessor runs with the new values:

// Add or update a custom define
material.defines = material.defines || {};
material.defines.USE_CUSTOM_EFFECT = 1;

// Recompile shader to evaluate the new preprocessor directive
material.version++;

material.version vs. material.needsUpdate

In standard Three.js source code, the needsUpdate setter is defined as:

set needsUpdate( value ) {
  if ( value === true ) this.version ++;
}

Incrementing material.version++ achieves the exact same result directly. It guarantees that the internal WebGL state recognizes the change on the subsequent renderer.render() call, forcing the driver to regenerate the vertex and fragment shaders without requiring you to construct a brand-new material instance.

How to Calculate Float32Array Memory in Three.js

Calculating the exact memory footprint of a Float32Array used as a position BufferAttribute in Three.js involves evaluating two distinct memory tiers: the raw binary buffer data (allocated in both system RAM and GPU VRAM) and the JavaScript engine's internal object overhead in the V8 heap. This guide details the formulas, properties, and runtime considerations needed to compute the exact byte consumption for both CPU and GPU allocations.

1. Raw Binary Data Size

The primary memory consumer of a BufferAttribute is its underlying ArrayBuffer. A Float32Array represents 32-bit floating-point numbers, meaning each individual numerical element consumes 4 bytes (\(32 \text{ bits} / 8 = 4 \text{ bytes}\)).

Because a standard position attribute in 3D space uses 3 components per vertex (\(X, Y, Z\)), the item size is 3.

To calculate the exact raw data size in bytes:

\[\text{Raw Data Bytes} = \text{vertex count} \times \text{itemSize} \times 4\]

In Three.js, you can read this directly using native JavaScript and Three.js properties:

const positionAttribute = geometry.getAttribute('position');

// Direct access via the underlying TypedArray
const rawBytes = positionAttribute.array.byteLength;

// Or via BufferAttribute properties
const calculatedBytes = positionAttribute.count * positionAttribute.itemSize * Float32Array.BYTES_PER_ELEMENT;

For example, a mesh containing 100,000 vertices:

  • Total elements: \(100{,}000 \times 3 = 300{,}000\) floats
  • Raw byte footprint: \(300{,}000 \times 4 = 1{,}200{,}000 \text{ bytes}\) (\(\approx 1.14 \text{ MB}\))

2. GPU VRAM Allocation

When the geometry is uploaded to the GPU via WebGL or WebGPU, Three.js transfers the raw binary buffer into a graphics buffer object.

The GPU memory footprint corresponds strictly to the aligned binary data:

  • GPU VRAM: Equal to positionAttribute.array.byteLength.
  • Position attributes do not incur JavaScript object overhead on the GPU, though drivers may occasionally add minimal memory padding depending on 16-byte alignment rules or uniform buffer constraints. For standard vertex buffer bindings (gl.ARRAY_BUFFER), the allocation matches byteLength precisely.

3. JavaScript Heap Overhead (CPU RAM)

In the browser's JavaScript engine (such as V8 in Chrome and Node.js), memory is occupied not only by the raw buffer but also by the wrapper objects referencing it.

On a standard 64-bit architecture with pointer compression:

  • ArrayBuffer header: ~32 to 48 bytes.
  • Float32Array view header: ~48 to 64 bytes (stores pointers to the buffer, byte offset, byte length, and prototype references).
  • THREE.BufferAttribute instance: ~56 to 80 bytes (stores properties like name, itemSize, count, normalized, usage, version, and update ranges).

Total JavaScript metadata overhead is typically between 136 and 192 bytes.

4. Consolidated Calculation Function

To get the comprehensive memory footprint across the CPU heap and GPU VRAM, implement the following function:

function getPositionAttributeMemory(attribute) {
  if (!(attribute.array instanceof Float32Array)) {
    throw new Error("Attribute is not a Float32Array.");
  }

  const bytesPerElement = Float32Array.BYTES_PER_ELEMENT; // 4
  const rawBytes = attribute.array.byteLength; // count * itemSize * 4
  
  // Approximate V8 metadata overhead for the wrappers on 64-bit runtimes
  const jsMetadataOverheadBytes = 160; 

  return {
    vertexCount: attribute.count,
    rawBytes: rawBytes,
    gpuVRAMBytes: rawBytes,
    cpuTotalBytes: rawBytes + jsMetadataOverheadBytes,
    megabytes: (rawBytes / (1024 * 1024)).toFixed(4)
  };
}

For small attributes, the ~160-byte JavaScript wrapper represents a measurable percentage of CPU memory. For production geometries containing thousands of vertices, the raw byteLength accounts for over 99.9% of the memory footprint.

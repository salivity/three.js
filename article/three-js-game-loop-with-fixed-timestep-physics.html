Three.js Game Loop with Fixed Timestep Physics

In Three.js applications, pairing visual rendering with a physics engine requires decoupling the rendering frame rate from the simulation update rate. While THREE.Clock.getDelta() provides the elapsed time between frames, passing this raw variable delta directly into physics calculations causes inconsistent simulation behavior, tunneling, and instability. This guide demonstrates how to structure a robust game loop using Clock.getDelta() alongside a fixed timestep accumulator pattern to guarantee deterministic, stable physics updates regardless of display refresh rates or frame drops.

The Flaw of Variable Delta Time in Physics

A standard animation loop relies on requestAnimationFrame, which executes at the display's refresh rate (typically 60Hz, 120Hz, or 144Hz) and can fluctuate under system load. If physics simulations use this dynamic delta directly:

// Problematic implementation
const delta = clock.getDelta();
physicsWorld.step(delta); // Unstable and non-deterministic

Small delta values can cause rounding errors, while large delta values (caused by backgrounding the tab or temporary frame drops) cause objects to teleport through colliders—a phenomenon known as tunneling.

The Fixed Timestep Accumulator Pattern

To achieve stability, physics must step forward in discrete, predictable increments (for example, exactly 60 times per second, or 1 / 60), independent of when frames are drawn.

The accumulator pattern works by:

  1. Measuring real elapsed time using clock.getDelta().
  2. Clamping the elapsed time to prevent the "spiral of death" during performance drops.
  3. Adding the elapsed time to an accumulator.
  4. Consuming the accumulated time in fixed-size chunks to advance the physics simulation.
  5. Rendering the Three.js scene once the accumulator is depleted.

Implementation

Below is the complete implementation of a robust Three.js loop using this pattern:

import * as THREE from 'three';

// 1. Initialize clock and scene components
const clock = new THREE.Clock();
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, window.innerWidth / window.innerHeight, 0.1, 1000);
const renderer = new THREE.WebGLRenderer({ antialias: true });

// 2. Define physics parameters
const fixedTimeStep = 1.0 / 60.0; // 60 Hz physics step
const maxSubSteps = 5;            // Max steps to prevent CPU lockups
let accumulator = 0.0;

  // Clamp the delta to avoid spiral of death (e.g., after switching browser tabs)
  if (delta > 0.25) {
    delta = 0.25;
  }

  accumulator += delta;

  // Consume accumulated time in fixed increments
  let steps = 0;
  while (accumulator >= fixedTimeStep && steps < maxSubSteps) {
    updatePhysics(fixedTimeStep);
    accumulator -= fixedTimeStep;
    steps++;
  }

  // Update Three.js object transforms to match physics states
  updateVisuals();

  // Render the frame
  renderer.render(scene, camera);
}

Key Considerations for Stability

  • The Spiral of Death: If the physics step takes longer to compute than the fixedTimeStep, the accumulator continuously increases. Clamping delta (to 0.25 seconds or similar) and enforcing a maxSubSteps safety cap ensures the loop drops physics time rather than freezing the browser tab completely.
  • Transform Synchronization: Update your Three.js mesh transforms after the while loop finishes. Updating mesh matrices inside the fixed update loop wastes CPU cycles, as only the final calculated state needs to be displayed to the user for that rendered frame.

Three.js CubeCamera RenderTarget Memory Management

Dynamic reflections in Three.js rely on the CubeCamera to render scenes across six orientations into an internal cube render target, which is computationally expensive and memory-intensive. Without explicit memory management, continually instantiating or resizing these targets causes significant GPU memory leaks, leading to frame drops and WebGL context crashes. This article explains how to efficiently allocate, reuse, and explicitly dispose of a WebGLCubeRenderTarget when working with a CubeCamera.

The Cause of Memory Leaks with CubeCamera

A CubeCamera does not store the visual data itself; it renders into a WebGLCubeRenderTarget. Each cube render target allocates six separate 2D textures on the GPU to form a cubemap, along with corresponding depth and stencil buffers.

Because JavaScript's garbage collector only manages system RAM and cannot release GPU-allocated WebGL resources, dereferencing a CubeCamera or its render target leaves those framebuffers and textures stranded in VRAM. You must invoke Three.js disposal methods explicitly to reclaim this space.

1. Reuse a Single WebGLCubeRenderTarget

Avoid creating new instances of CubeCamera or WebGLCubeRenderTarget inside your animation loop. Instead, allocate the render target once during initialization and update the camera conditionally:

import * as THREE from 'three';

// 1. Initialize render target and camera once
const cubeRenderTarget = new THREE.WebGLCubeRenderTarget(256, {
  generateMipmaps: true,
  minFilter: THREE.LinearMipmapLinearFilter,
  magFilter: THREE.LinearFilter,
  format: THREE.RGBAFormat,
});

const cubeCamera = new THREE.CubeCamera(0.1, 1000, cubeRenderTarget);
scene.add(cubeCamera);

// Assign the target's texture to a material
reflectiveMaterial.envMap = cubeRenderTarget.texture;
reflectiveMaterial.needsUpdate = true;

When rendering dynamic reflections, only call cubeCamera.update() when the scene geometry or lighting changes, rather than every frame, to conserve GPU bandwidth:

function render() {
  requestAnimationFrame(render);

  // Hide the reflective object to prevent it from rendering inside its own cubemap
  reflectiveMesh.visible = false;
  
  // Render the cubemap
  cubeCamera.update(renderer, scene);
  
  reflectiveMesh.visible = true;
  renderer.render(scene, camera);
}

2. Explicitly Disposing of the Render Target

When removing the reflective object, changing levels, or unmounting a scene, you must explicitly release the WebGL resources tied to the target:

function disposeDynamicReflections(cubeCamera, cubeRenderTarget) {
  // Remove camera from the scene graph
  if (cubeCamera.parent) {
    cubeCamera.parent.remove(cubeCamera);
  }

  // Dispose of the target and its texture memory
  if (cubeRenderTarget) {
    cubeRenderTarget.dispose();
  }
}

Calling cubeRenderTarget.dispose() deletes the underlying WebGL framebuffers, renderbuffers, and cubemap textures from GPU memory.

3. Handling Resolution Resizing Properly

If you dynamically adjust reflection quality or respond to viewport changes, do not create a new WebGLCubeRenderTarget without cleaning up the old one:

function resizeCubeRenderTarget(newSize) {
  // Discard previous GPU allocations
  cubeRenderTarget.dispose();

  // Allocate new target
  cubeRenderTarget = new THREE.WebGLCubeRenderTarget(newSize, {
    generateMipmaps: true,
    minFilter: THREE.LinearMipmapLinearFilter,
    magFilter: THREE.LinearFilter,
  });

  // Re-link target to the camera and material
  cubeCamera.renderTarget = cubeRenderTarget;
  reflectiveMaterial.envMap = cubeRenderTarget.texture;
  reflectiveMaterial.needsUpdate = true;
}

4. Cleaning Up PMREM Targets

If you process the cubemap through PMREMGenerator to achieve blurred, rough reflections on PBR materials (MeshStandardMaterial or MeshPhysicalMaterial), the generator outputs an additional render target. You must dispose of that generated texture as well:

const pmremGenerator = new THREE.PMREMGenerator(renderer);
let dynamicEnvMap = pmremGenerator.fromCubemap(cubeRenderTarget.texture).texture;

// During cleanup:
dynamicEnvMap.dispose();
pmremGenerator.dispose();
cubeRenderTarget.dispose();

Failing to dispose of the PMREM texture will result in residual textures lingering in memory, neutralizing the benefits of disposing the base cube render target.

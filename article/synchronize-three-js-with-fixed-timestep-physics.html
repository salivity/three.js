Synchronize Three.js with Fixed Timestep Physics

Coupling a physics simulation directly to the variable frame rate of Three.js leads to unpredictable behavior, non-deterministic movement, and unstable collision detection. This article explains how to decouple your rendering loop from your physics updates using a fixed time step and a delta time accumulator. By implementing this pattern, you ensure consistent, deterministic physics simulations across different display refresh rates while keeping Three.js rendering completely smooth.

The Variable Frame Rate Problem

The browser's requestAnimationFrame loop executes at the display's refresh rate (typically 60Hz, 120Hz, or 144Hz) and can fluctuate during heavy CPU/GPU loads. Passing this variable delta time (deltaTime) directly to a physics engine (such as Cannon-es, Rapier, or Ammo.js) introduces calculation errors. A sudden frame drop can cause a large delta step, pushing objects through colliders (tunneling) or causing constraint explosions.

The Accumulator Pattern

The delta time accumulator solves this by consuming variable elapsed time in fixed, predictable slices.

  1. Calculate Delta Time: Measure elapsed time since the previous frame.
  2. Cap the Delta: Clamp large delta spikes (caused by background tab switching or heavy lag) to prevent the "spiral of death," where the engine gets stuck computing infinite catch-up steps.
  3. Accumulate Time: Add the clamped frame time to an accumulator variable.
  4. Step Physics in Fixed Slices: While the accumulator is greater than or equal to your fixed time step (e.g., 1/60th of a second), update the physics simulation by that exact fixed step and subtract it from the accumulator.
  5. Interpolate (Optional but Recommended): Use the remaining time in the accumulator to interpolate mesh positions between the previous and current physics states for visually smooth rendering.

Implementation Example

Below is a complete implementation using Three.js and a generic physics engine interface:

import * as THREE from 'three';

const clock = new THREE.Clock();

// Configuration
const FIXED_TIME_STEP = 1 / 60; // 60 Hz physics update (approx. 0.01666s)
const MAX_DELTA_TIME = 0.1;     // Maximum frame time capped to avoid death spiral
let accumulator = 0.0;

function animate() {
    requestAnimationFrame(animate);

    // 1. Get raw elapsed frame time
    let frameTime = clock.getDelta();

    // 2. Clamp frame time to prevent spiraling on large stutters
    if (frameTime > MAX_DELTA_TIME) {
        frameTime = MAX_DELTA_TIME;
    }

    // 3. Add to the accumulator
    accumulator += frameTime;

    // 4. Consume accumulator in fixed steps
    while (accumulator >= FIXED_TIME_STEP) {
        // Save previous transforms here if using interpolation
        physicsWorld.step(FIXED_TIME_STEP);
        accumulator -= FIXED_TIME_STEP;
    }

    // 5. Update Three.js meshes to match physics bodies
    syncTransforms();

    // 6. Render the scene
    renderer.render(scene, camera);
}

Eliminating Visual Jitter with Interpolation

Because the rendering loop and physics ticks rarely align perfectly, the remaining time in the accumulator represents a partial tick. Rendering the scene without accounting for this remainder can create micro-stuttering, especially on high-refresh-rate monitors (120Hz+).

To eliminate this, calculate an alpha value between 0.0 and 1.0:

\[\alpha = \frac{\text{accumulator}}{\text{FIXED\_TIME\_STEP}}\]

Use this alpha value to linearly interpolate (LERP) mesh positions and spherically interpolate (SLERP) mesh quaternions between the previous physics state and the current physics state before rendering:

// Calculate interpolation factor
const alpha = accumulator / FIXED_TIME_STEP;

// Interpolate positions and rotations
mesh.position.lerpVectors(previousBodyPosition, currentBodyPosition, alpha);
mesh.quaternion.slerpQuaternions(previousBodyRotation, currentBodyRotation, alpha);

By storing the transform before physicsWorld.step() runs and blending toward the post-step transform using alpha, the visual representation remains completely fluid regardless of the discrepancy between the display rate and physics rate.

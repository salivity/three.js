WebGPU Compute Shaders for Particles in Three.js

Three.js leverages the modern WebGPURenderer to execute general-purpose GPU computing, allowing developers to simulate millions of particles at interactive framerates. By using compute shaders managed through the Three.js Shading Language (TSL) and ComputeNode, the engine updates complex particle physics—such as velocity, position, and collision—directly in GPU memory. This approach eliminates the performance overhead of transferring data between the CPU and GPU, feeding simulated data seamlessly into render passes.

The Compute Pipeline Architecture

In traditional WebGL implementations, particle updates either relied on CPU loops or complex workarounds like transform feedback or render-to-texture ping-pong techniques. WebGPURenderer eliminates these workarounds by providing native access to WebGPU compute pipelines.

The compute pipeline runs independently of the standard vertex and fragment pipelines. Compute shaders operate on multi-dimensional grids of workgroups, executing arbitrary mathematical operations on structured buffers in parallel. In Three.js, these operations are typically declared using TSL nodes, which abstract raw WGSL (WebGPU Shading Language) into a modular, chainable node graph.

Buffer Management and Data Binding

Particle data—such as position, velocity, mass, and lifetime—is stored in GPU-accessible storage buffers. Three.js manages these via StorageInstancedBufferAttribute or StorageBufferNode.

  1. Storage Allocation: An array buffer is initialized on the GPU containing the initial state of the particle system.
  2. Buffer Binding: The buffer is bound as a read-write storage buffer within the compute pass, allowing compute threads to read previous state values, calculate updates, and write new values back into the exact same memory space.
  3. Direct Render Binding: The same storage buffer is simultaneously bound to an InstancedMesh or a point cloud material as an attribute. Because the data remains on the GPU, the rendering pass immediately draws the updated transforms without memory re-allocation or host-device transfers.

Executing Compute Nodes

To run the simulation, Three.js provides the ComputeNode abstraction. A compute node encapsulates the logic executed by each thread across specified workgroup counts:

  • Logic Definition: Developers write simulation rules (e.g., gravity, drag, turbulence fields) using TSL operations, binding storage buffers via storage() nodes.
  • Dispatch: The compute pass is dispatched explicitly via renderer.compute(computeNode) during the animation loop prior to calling renderer.render(scene, camera).
  • Synchronization: WebGPU automatically handles pipeline barriers. The renderer ensures compute write operations complete before the vertex shader attempts to read from the storage buffer in the subsequent render pass, preventing race conditions.

Benefits for Advanced Simulations

By offloading calculations to compute shaders via WebGPURenderer, particle systems gain distinct advantages:

  • Massive Concurrency: Thread dispatch sizes can scale to millions of elements while keeping the main JavaScript thread completely unblocked.
  • Complex Interactions: Compute shaders support random memory read-write operations, enabling inter-particle collision, spatial hashing, flocking (Boids), and fluid simulations (SPH) that are impractical in standard vertex or fragment shaders.
  • Deterministic Performance: Because data transfers over the PCIe bus are avoided entirely after initialization, frame times remain stable regardless of particle count.

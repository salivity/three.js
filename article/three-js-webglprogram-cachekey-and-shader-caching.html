Three.js WebGLProgram cacheKey and Shader Caching

In Three.js, compiling WebGL shader programs is a performance-heavy task. To optimize rendering, the engine caches compiled shaders using an internal identifier managed through WebGLProgram. This article covers how the shader program caching mechanism works, why shader conflicts occur when modifying materials, and how to use the customProgramCacheKey property to manually alter the cache key and force unique shader compilations.

What is WebGLProgram.cacheKey?

Every time a material is prepared for rendering, Three.js generates a unique string identifier representing the compiled shader: the program's cache key. Under the hood, the WebGLPrograms manager maintains an internal pool of active WebGLProgram instances.

Instead of compiling a new GLSL program for every mesh or material instance, Three.js checks whether a program with the same configuration already exists. The generated cache key encapsulates all structural shader variables, including:

  • Vertex and fragment shader prefixes and defines
  • Active lights and shadow configurations
  • Enabled texture map channels (roughness, metalness, normal maps, etc.)
  • Instancing, clipping planes, and fog settings

If two materials generate the identical cache key, Three.js reuses the existing compiled WebGLProgram, bypassing costly WebGL API compilation calls (gl.compileShader and gl.linkProgram).

The Shader Sharing Problem with onBeforeCompile

A common pitfall arises when customizing built-in materials using Material.onBeforeCompile. Because onBeforeCompile dynamically modifies the GLSL code directly before it is passed to the WebGL compiler, Three.js cannot automatically inspect the injected string modifications.

If you have two instances of MeshStandardMaterial with the exact same base properties (e.g., color, roughness, light setup), but inject different GLSL logic via onBeforeCompile, Three.js will calculate an identical cache key for both. As a result, the engine assigns the first compiled shader to both materials, ignoring the modifications made to the second material.

How to Manually Alter the Cache Key

To prevent collisions and force unique shader compilation, Three.js provides the customProgramCacheKey method on the base Material class.

By default, material.customProgramCacheKey returns an empty string. When implemented, the returned string is appended directly into the internal cache key generation logic inside WebGLPrograms.

Implementation Example

To force Three.js to compile a unique WebGLProgram for customized materials, assign a function returning a distinct identifier to customProgramCacheKey:

import * as THREE from 'three';

const materialA = new THREE.MeshStandardMaterial({ color: 0xff0000 });
const materialB = new THREE.MeshStandardMaterial({ color: 0xff0000 });

// Customize Material A
materialA.onBeforeCompile = (shader) => {
  shader.fragmentShader = shader.fragmentShader.replace(
    '#include <dithering_fragment>',
    '#include <dithering_fragment>\ngl_FragColor.rgb *= 0.5;'
  );
};
materialA.customProgramCacheKey = () => 'custom_darken_effect';

// Customize Material B with different logic
materialB.onBeforeCompile = (shader) => {
  shader.fragmentShader = shader.fragmentShader.replace(
    '#include <dithering_fragment>',
    '#include <dithering_fragment>\ngl_FragColor.rgb += vec3(0.2);'
  );
};
materialB.customProgramCacheKey = () => 'custom_brighten_effect';

Because customProgramCacheKey returns different strings (custom_darken_effect and custom_brighten_effect), Three.js treats them as separate entities, compiling two distinct WebGLProgram instances despite identical baseline material parameters.

Dynamic Cache Keys

If the injected shader depends on specific configuration parameters, ensure those parameters are serialized into the cache key string:

material.userData.effectIntensity = 2.0;

material.customProgramCacheKey = function () {
  return `dissolveEffect_${this.userData.effectIntensity > 0 ? 'enabled' : 'disabled'}`;
};

When changing the returned value of customProgramCacheKey during runtime, set material.needsUpdate = true to inform Three.js that it must evaluate the cache and recompile the program for the next frame.

Best Practices

  • Avoid non-deterministic keys: Never return random numbers (such as Math.random()) or timestamps. Doing so causes memory leaks by continually compiling and storing redundant WebGL programs in the cache.
  • Reuse keys when shaders are identical: If multiple materials use the same injected shader alterations, they should return the identical customProgramCacheKey. This ensures that they share the compiled program instead of duplicating it.

Three.js geometry.dispose() with Mesh in Scene

When you invoke geometry.dispose() on a Three.js BufferGeometry while its parent Mesh remains inside an active scene graph, the WebGL buffers are immediately deleted from GPU memory. However, because the mesh is still marked as visible in the render loop, the renderer will typically recreate those buffers and re-upload the geometry data back to the GPU on the very next frame, causing performance stutters, unintended memory churn, or rendering errors.

Immediate GPU Buffer Deallocation

When geometry.dispose() executes, the geometry instance dispatches an internal dispose event. The WebGLRenderer—specifically the internal WebGLGeometries and WebGLAttributes modules—listens for this event.

Upon receiving the event, the renderer:

  1. Locates the WebGL buffer references associated with the geometry's attributes (such as position, normal, uv, and index buffers).
  2. Calls the underlying WebGL API command gl.deleteBuffer() on each attribute buffer.
  3. Removes the internal cache entries that link the BufferGeometry ID to those GPU allocations.

At this exact moment, the GPU video RAM (VRAM) previously occupied by those vertex buffers is marked as freed.

The Next Frame: Automatic Buffer Recreation

The problem arises on the subsequent invocation of renderer.render(scene, camera).

During the render pass, Three.js traverses the scene graph. When it encounters the Mesh, it verifies that the mesh is visible and attempts to bind its geometry for drawing. Because geometry.dispose() purged the cached WebGL buffers, the renderer detects that the GPU has no record of this geometry.

If the underlying JavaScript arrays (Float32Array or Uint16Array on the geometry attributes) still exist in CPU memory:

  • Three.js treats the geometry as new.
  • It allocates fresh WebGL buffers via gl.createBuffer().
  • It transfers the attribute data across the PCIe bus back to the GPU via gl.bufferData().

Consequently, the GPU memory you freed is immediately re-allocated. If you call dispose() continuously inside your render loop without detaching the mesh, this creates a severe performance bottleneck known as memory thrashing, characterized by massive frame-rate drops and CPU-to-GPU bandwidth saturation.

Missing CPU Data and WebGL Errors

If you modified, cleared, or set the CPU-side attribute arrays to null after calling geometry.dispose(), the renderer will not be able to re-upload the vertex data.

In this scenario:

  • WebGL attempts to draw an incomplete or empty buffer binding.
  • The browser console will emit WebGL warnings or errors (such as glDrawElements: attempt to render with no buffer attached to enabled attribute).
  • The mesh will either vanish from the screen, turn completely black, or render as corrupted geometry artifacts.

CPU Memory Remains Intact

Calling dispose() only targets GPU resources; it has no effect on JavaScript memory. Because the Mesh is still attached to the Scene (or another parent Object3D), strong references to both the mesh and its geometry property remain active. As a result, the JavaScript engine's garbage collector cannot free the CPU-side vertex data, retaining the object in system RAM.

The Correct Removal Procedure

To permanently remove a mesh and its resources without triggering re-allocations:

  1. Remove from the scene graph first: Call mesh.parent.remove(mesh) or scene.remove(mesh).
  2. Dispose of the geometry: Call mesh.geometry.dispose().
  3. Dispose of the material: Call mesh.material.dispose(), along with any attached textures via material.map.dispose().
  4. Sever the reference: Set references to the mesh to null to allow CPU garbage collection.

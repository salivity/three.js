Three.js WebGLProgram Caching Mechanism Explained

Compiling WebGL shaders and linking them into GPU programs is one of the most performance-intensive operations in real-time 3D rendering. To prevent frame drops and redundant GPU overhead, Three.js implements an internal caching subsystem managed by the WebGLPrograms module. This mechanism evaluates the rendering state, scene configuration, and material parameters to generate a unique cache signature, ensuring that identical shader configurations share a single compiled WebGLProgram instance across multiple meshes.

The Role of WebGLPrograms

At the core of the caching architecture is the WebGLPrograms manager, initialized internally by WebGLRenderer. Compiling a GLSL shader requires calls to WebGL APIs like gl.compileShader() and gl.linkProgram(), which block CPU-GPU execution. To minimize these operations, Three.js delegates all program generation requests to WebGLPrograms.acquireProgram(). Instead of blindly compiling a new program whenever a material is used, the renderer queries this manager to check whether a matching program has already been built.

Generating the Program Cache Key

The identification process relies on generating a deterministic string key representing the final state of the shader. Three.js evaluates several input parameters through internal helper methods like getProgramCode() to form this key:

  • Material Properties and Defines: Custom GLSL #define directives, material types (e.g., MeshStandardMaterial, MeshBasicMaterial), precision settings, and boolean flags such as wireframe, transparent, or fog.
  • Scene and Environment State: Active lighting types (directional, point, spot, ambient), shadow map configurations, environment maps, and active tone mapping or color space transformations.
  • Geometry Capabilities: Mesh attributes such as vertex colors, morph targets, skinning indices, UV channels, and instanced rendering parameters.
  • Shader Snippets (ShaderChunks): Injected GLSL blocks provided directly or through plugins such as onBeforeCompile.

Rather than executing an expensive full-text hash of the entire GLSL source code, Three.js builds a concatenated string containing these configuration parameters along with the vertex and fragment shader IDs. This generated string acts as the fingerprint for the required GPU program.

Program Retrieval and Reference Counting

The WebGLPrograms instance maintains an internal array of cached program entries. When acquireProgram() is executed during a render pass:

  1. The renderer calculates the cache key (code) for the given material and rendering state.
  2. The manager iterates through existing program records to find a match where entry.code === code.
  3. If an identical key is located, Three.js reuses the corresponding WebGLProgram instance without executing any WebGL compilation calls.
  4. The entry’s reference count (usedTimes) increments by one, tracking how many active materials or objects depend on that specific GPU program.

Compilation of New Programs

If no match exists for the generated key, Three.js initiates the compilation sequence:

  1. A new WebGLProgram object is instantiated.
  2. The GLSL code is resolved by expanding Three.js ShaderChunk definitions, applying preprocessor macros, and binding attributes and uniforms.
  3. The vertex and fragment shaders are compiled and linked via the native WebGL context.
  4. The resulting WebGLProgram is packaged alongside its cache key and reference count (usedTimes = 1), then stored in the cache array for future render cycles.

Program Disposal and Cleanup

When a material is disposed of using material.dispose(), Three.js calls WebGLPrograms.releaseProgram(). The manager decrements the usedTimes counter for that program. When usedTimes reaches zero—meaning no active materials in the scene depend on that shader configuration—the program is unlinked, deleted from GPU memory using gl.deleteProgram(), and permanently removed from the internal cache list.

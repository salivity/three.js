Optimizing Three.js Culling with Frustum containsPoint

In high-complexity Three.js applications, standard view-frustum culling can strain the CPU when transforming and recomputing detailed bounding volumes for thousands of meshes or dynamically deformed geometries. This article outlines how to implement a two-stage culling optimization that uses Frustum.containsPoint() as an early-acceptance gate. By testing an object's pre-existing center point first, you can instantly flag clearly visible objects and bypass expensive bounding-box calculations and world-matrix updates for the majority of the scene.

The Problem with Default Bounding Calculations

By default, Three.js updates a mesh’s world matrix and evaluates frustum.intersectsSphere(sphere) against the object's geometry.boundingSphere. For complex meshes, geometries requiring updated computeBoundingBox() calls (such as morph targets or procedurally updated buffers), or scenes with thousands of nodes, these matrix transformations and bounds evaluations create measurable frame-time overhead on the main thread.

The Fast-Accept Strategy

A point-in-frustum test requires only six dot-product operations against the frustum's bounding planes. If an object’s central world coordinate is fully contained within the frustum, and the object is small relative to the field of view, the mesh is guaranteed to be partially or completely visible.

By using Frustum.containsPoint() as a "fast-accept" test, you can:

  1. Mark the object as visible immediately if the point resides inside the frustum.
  2. Only compute expensive, precise bounding volumes (such as regenerated bounding boxes or complex intersection routines) if the point test fails, because the mesh may still partially overlap the frustum boundaries.

Implementation

To bypass the engine's internal culling and run this check manually, set frustumCulled = false on target meshes and execute the test during the render loop or inside a pre-render update pass.

import * as THREE from 'three';

const frustum = new THREE.Frustum();
const projScreenMatrix = new THREE.Matrix4();
const meshWorldPos = new THREE.Vector3();

function cullScene(camera, dynamicMeshes) {
  // Update the frustum from the camera matrices
  projScreenMatrix.multiplyMatrices(camera.projectionMatrix, camera.matrixWorldInverse);
  frustum.setFromProjectionMatrix(projScreenMatrix);

  for (let i = 0; i < dynamicMeshes.length; i++) {
    const mesh = dynamicMeshes[i];
    
    // Retrieve world position of the object's pivot or center
    mesh.getWorldPosition(meshWorldPos);

    // Step 1: Rapid Point Check (Fast-Accept)
    if (frustum.containsPoint(meshWorldPos)) {
      mesh.visible = true;
      continue; // Skip expensive bounds recalculation
    }

    // Step 2: Fallback to Precise Intersection Test
    // Only execute heavy bounds calculations when the center point is outside
    if (!mesh.geometry.boundingBox) {
      mesh.geometry.computeBoundingBox();
    }
    
    // Transform bounding box to world space for the boundary test
    const worldBox = mesh.geometry.boundingBox.clone().applyMatrix4(mesh.matrixWorld);
    
    mesh.visible = frustum.intersectsBox(worldBox);
  }
}

Critical Considerations

  • Conservative Fast-Accept: This pattern operates as a fast-accept, not a fast-reject. If containsPoint returns false, you cannot discard the mesh immediately; its geometry may still overlap the frustum edge.
  • Anchor Positioning: Ensure the test point represents the true center of the geometry rather than an offset origin. You can pre-calculate the local bounding center during asset loading and transform that specific point to world space to prevent premature fallbacks.
  • Garbage Collection: Avoid allocating temporary Vector3 or Matrix4 instances inside the loop. Reuse static scratch variables to eliminate per-frame garbage collection pauses.

Optimize Raycasting on 1M+ InstancedMesh in Three.js

Raycasting against an InstancedMesh with over one million instances causes severe CPU bottlenecks in Three.js because the default implementation performs an \(O(N)\) linear scan, evaluating matrix transformations and geometry intersections for every instance. To maintain interactive frame rates, developers must bypass standard raycaster routines in favor of mathematical optimizations. This article details how to reduce this workload from linear to logarithmic or constant time using spatial hierarchies, local-space ray inversion, analytical bounding primitives, and GPU-driven picking.

The Mathematical Bottleneck of Native Raycasting

In Three.js, executing Raycaster.intersectObject() on an InstancedMesh forces the CPU to iterate through all \(N\) instances (\(N > 1,000,000\)). For each instance \(i\), the engine retrieves the instance matrix \(\mathbf{M}_i\), computes its inverse \(\mathbf{M}_i^{-1}\), transforms the world-space ray into local space, and checks for intersection against geometry faces.

Performing one million \(4 \times 4\) matrix operations and subsequent bounding tests on the main JavaScript thread will routinely exceed the 16.6ms frame budget, dropping the application to sub-interactive frame rates.

Step 1: Inverse Ray Transformation (Local-Space Testing)

Transforming geometry vertices into world space for intersection testing is computationally expensive. The optimal approach is to transform the single world-space ray into each instance's local coordinate system:

Given a ray with origin \(\mathbf{o}\) and normalized direction \(\mathbf{d}\):

\[\mathbf{o}_{\text{local}} = \mathbf{M}_i^{-1} \begin{bmatrix} \mathbf{o} \\ 1 \end{bmatrix}, \quad \mathbf{d}_{\text{local}} = \mathbf{M}_i^{-1} \begin{bmatrix} \mathbf{d} \\ 0 \end{bmatrix}\]

Because the direction vector is a direction, the translation component of \(\mathbf{M}_i^{-1}\) is ignored (\(w = 0\)). After transforming the direction, normalize \(\mathbf{d}_{\text{local}}\) to compute accurate hit distances, or retain its magnitude to simplify distance scaling calculations:

\[t_{\text{world}} = t_{\text{local}} \cdot \|\mathbf{d}_{\text{local}}\|\]

Step 2: Spatial Partitioning with a World-Space BVH

To avoid evaluating one million matrices, partition the instance positions using a spatial data structure such as a Bounding Volume Hierarchy (BVH) or an Octree. This reduces query complexity from \(O(N)\) to \(O(\log N)\).

  1. AABB Construction: For each instance, compute an Axis-Aligned Bounding Box (AABB) in world space: \[\mathbf{c}_{\text{world}} = \mathbf{M}_i \mathbf{c}_{\text{local}}\] Expand the box dimensions based on the instance scale factors derived from the matrix.
  2. Ray-AABB Slab Test: Traverse the BVH using the Kay-Kajiya slab method. For a ray and an axis-aligned box defined by minimum bounds \(\mathbf{p}_{\min}\) and maximum bounds \(\mathbf{p}_{\max}\): \[t_{1, \text{axis}} = \frac{p_{\min, \text{axis}} - o_{\text{axis}}}{d_{\text{axis}}}, \quad t_{2, \text{axis}} = \frac{p_{\max, \text{axis}} - o_{\text{axis}}}{d_{\text{axis}}}\] \[t_{\text{enter}} = \max(\min(t_{1,x}, t_{2,x}), \min(t_{1,y}, t_{2,y}), \min(t_{1,z}, t_{2,z}))\] \[t_{\text{exit}} = \min(\max(t_{1,x}, t_{2,x}), \max(t_{1,y}, t_{2,y}), \max(t_{1,z}, t_{2,z}))\] An intersection occurs if \(t_{\text{enter}} \le t_{\text{exit}}\) and \(t_{\text{exit}} \ge 0\).

Traversing the BVH isolates candidate instances down from \(1,000,000\) to fewer than \(10\) per frame.

Step 3: Analytical Bounding Sphere Early-Exit

Before running detailed triangle-level intersection tests on the remaining candidates, run an analytical ray-sphere test.

Represent the bounding sphere at center \(\mathbf{c}\) with radius \(r\):

  1. Compute the vector from the ray origin to the center: \(\mathbf{v} = \mathbf{c} - \mathbf{o}\).
  2. Project \(\mathbf{v}\) onto the ray direction: \(t_{\text{projection}} = \mathbf{v} \cdot \mathbf{d}\).
  3. Calculate the squared perpendicular distance from the sphere center to the ray: \[d_{\perp}^2 = \|\mathbf{v}\|^2 - (t_{\text{projection}})^2\]
  4. If \(d_{\perp}^2 > r^2\), the ray misses the sphere entirely, avoiding local matrix inversion and mesh analysis.

Step 4: The Hardware Alternative: GPU Color-ID Picking

When instances exceed several millions or geometry undergoes dynamic GPU deformation, analytical CPU raycasting can be replaced with GPU picking.

  1. Create an off-screen WebGLRenderTarget with a dimensions of \(1 \times 1\) pixel, centered at the cursor coordinate.
  2. Use an override material on the InstancedMesh that encodes the gl_InstanceID into RGB values: \[R = \lfloor \text{id} / 65536 \rfloor \pmod{256} / 255.0\] \[G = \lfloor \text{id} / 256 \rfloor \pmod{256} / 255.0\] \[B = (\text{id} \pmod{256}) / 255.0\]
  3. Render the scene using a scissor test constrained to the \(1 \times 1\) target area.
  4. Read the single pixel using gl.readPixels(): \[\text{Instance ID} = (R \times 65536) + (G \times 256) + B\]

This approach operates in \(O(1)\) CPU time, moving matrix transformations and depth testing entirely to the GPU rasterization pipeline.

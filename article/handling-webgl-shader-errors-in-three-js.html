Handling WebGL Shader Errors in Three.js

This guide explains how to safely intercept, debug, and handle WebGL initialization and shader compilation issues in Three.js. You will learn how to detect WebGL context creation failures, how to leverage the WebGLRenderer.debug.checkShaderErrors property to catch broken shaders during development, and how to safely toggle these checks to maintain high frame rates in production environments.

Detecting WebGL Context Creation Failures

Before dealing with shader errors, you must ensure the client device successfully creates a WebGL context. If the browser or hardware lacks WebGL support, instantiating THREE.WebGLRenderer throws an error.

Wrap the renderer initialization in a try...catch block to handle setup failures gracefully:

import * as THREE from 'three';

let renderer;

try {
  renderer = new THREE.WebGLRenderer({ antialias: true });
} catch (error) {
  console.error("WebGL context creation failed:", error);
  displayFallbackUI("WebGL is not supported or disabled on your device.");
}

function displayFallbackUI(message) {
  const notice = document.createElement('div');
  notice.className = 'webgl-error-fallback';
  notice.innerText = message;
  document.body.appendChild(notice);
}

Using WebGLRenderer.debug.checkShaderErrors

The renderer.debug.checkShaderErrors property is a boolean flag that determines whether Three.js checks material shader programs for compilation and linking errors.

  • Enabled (true): Three.js queries the WebGL context using gl.getShaderParameter() and gl.getProgramParameter() after compiling materials. If errors occur, detailed logs—including the invalid GLSL code line—are output to console.error.
  • Disabled (false): Three.js bypasses shader validation calls. This eliminates synchronous GPU-to-CPU stalls, drastically improving performance when uploading many materials.

By default, checkShaderErrors is set to true. You can configure it immediately after instantiating your renderer:

renderer.debug.checkShaderErrors = process.env.NODE_ENV !== 'production';

Safely Intercepting Shader Compilation Errors

Three.js logs shader errors directly to the browser console rather than throwing catchable JavaScript exceptions during draw calls. To capture, report, or display these errors within your application UI, intercept console.error calls originating from the WebGL program validation routine:

function monitorShaderErrors(renderer, onErrorCallback) {
  const originalConsoleError = console.error;

  console.error = function (...args) {
    const message = args.join(' ');
    
    // Check if the log matches Three.js shader compilation failures
    if (message.includes('THREE.WebGLShader: gl.getShaderInfoLog()') || 
        message.includes('THREE.WebGLProgram: gl.getProgramInfoLog()')) {
      onErrorCallback({
        type: 'ShaderCompilationError',
        details: args
      });
    }

    // Preserve standard console output
    originalConsoleError.apply(console, args);
  };
}

// Usage:
renderer.debug.checkShaderErrors = true;

monitorShaderErrors(renderer, (error) => {
  reportToTelemetryService(error);
});

Managing WebGL Context Loss

Shader errors and runtime GPU crashes can trigger WebGL context loss. To prevent unhandled crashes, attach listeners for webglcontextlost and webglcontextrestored to the renderer's canvas:

const canvas = renderer.domElement;

canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault(); // Informs the browser not to discard the context permanently
  console.warn('WebGL context lost. Pausing rendering loop.');
  cancelAnimationFrame(animationFrameId);
}, false);

canvas.addEventListener('webglcontextrestored', () => {
  console.info('WebGL context restored. Re-initializing resources.');
  reinitializeScene();
}, false);

Recommended Best Practices

  1. Development Mode: Set renderer.debug.checkShaderErrors = true to catch GLSL syntax and linking errors immediately during development.
  2. Production Mode: Explicitly set renderer.debug.checkShaderErrors = false. Querying shader status requires synchronous round-trips to the GPU, causing pipeline stalls when loading new assets dynamically.
  3. Custom Shader Development: When building custom ShaderMaterial or RawShaderMaterial instances, test with checkShaderErrors enabled locally to capture malformed vertex and fragment source code before deploying.

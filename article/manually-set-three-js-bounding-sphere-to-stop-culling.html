Manually Set Three.js Bounding Sphere to Stop Culling

Frustum culling in Three.js relies on an object's bounding sphere to determine whether a mesh intersects the camera's view frustum before drawing it to the screen. During fast camera movements, animated vertex displacement, or latency in matrix updates, these calculations can misjudge visibility and cause the mesh to pop out of view or flicker. This guide demonstrates how to directly manipulate and expand a geometry’s boundingSphere to ensure robust visibility during rapid camera motion without disabling frustum culling entirely.

Why Fast Camera Movements Cause Culling Issues

Three.js optimizes scene performance by testing the camera's view frustum against mesh.geometry.boundingSphere. By default, this sphere is calculated tightly around the raw, static vertex data using geometry.computeBoundingSphere().

When a camera pans or rotates at high velocity, motion blur, fast interpolation, or delays in matrix updates across animation frames can place the tight bounding sphere just outside the frustum planes before the visual elements have completely left the screen. The renderer interprets this as the object being off-screen and immediately drops it from the render pipeline.

While setting mesh.frustumCulled = false prevents the object from ever being hidden, it discards an essential rendering optimization. Manually expanding or defining the bounding sphere provides a safe middle ground.

Overriding the Bounding Sphere Manually

You can assign a custom THREE.Sphere directly to mesh.geometry.boundingSphere or expand the existing radius after computation.

Method 1: Expanding an Existing Bounding Sphere

If you already have a computed bounding sphere, you can artificially scale its radius to create a safety margin around the mesh:

// Compute the initial bounding sphere if it doesn't exist
if (!mesh.geometry.boundingSphere) {
    mesh.geometry.computeBoundingSphere();
}

// Add a buffer margin to the radius (e.g., 50% larger)
mesh.geometry.boundingSphere.radius *= 1.5;

This safety buffer ensures that during rapid camera sweeps, the mesh remains marked as visible even if the camera matrix lags slightly behind the rendered frame.

Method 2: Defining an Explicit Custom Bounding Sphere

For complex setups, dynamic vertex shaders, or meshes moving along wide trajectories, you can construct and assign an entirely new bounding sphere with a defined center and radius:

import * as THREE from 'three';

// Create a bounding sphere with a generous radius centered at the mesh's origin
const customCenter = new THREE.Vector3(0, 0, 0);
const customRadius = 100.0; // Set appropriate to your world units

mesh.geometry.boundingSphere = new THREE.Sphere(customCenter, customRadius);

If the mesh must never be culled under any circumstance, but you want to retain standard scene-graph architecture, you can set the radius to infinity:

mesh.geometry.boundingSphere = new THREE.Sphere(
    new THREE.Vector3(0, 0, 0),
    Infinity
);

Preventing Unintended Overwrites

Whenever you update buffer attributes or call functions like mesh.geometry.computeBoundingSphere(), Three.js recalculates and overwrites your manual modifications. To lock your custom bounding sphere:

  1. Avoid repetitive calls: Ensure geometry.computeBoundingSphere() is not being executed inside your requestAnimationFrame loop.
  2. Re-apply modifications after attribute changes: If you run operations that refresh geometry data (such as modifying position buffers), re-apply your custom radius or sphere immediately following the update.
  3. Lock the compute method (Optional): If third-party libraries or internal routines trigger recalculations unexpectedly, you can override the compute method on that specific geometry instance:
// Lock the compute function to prevent automatic recalculation
mesh.geometry.computeBoundingSphere = () => {};

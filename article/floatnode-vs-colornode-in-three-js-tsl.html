FloatNode vs ColorNode in Three.js TSL

In the Three.js Shading Language (TSL), constructing custom shaders requires composing modular nodes that represent values, operations, and attributes. While both floatNode and colorNode represent numeric data fed into shader pipelines, they differ fundamentally in their dimensionality, uniform buffer serialization, and color space awareness. This article breaks down the technical and structural differences between floatNode and colorNode when authoring node-based materials.

Dimensionality and Underlying Type

The most direct difference between the two nodes lies in their dimensionality and underlying shader data types:

  • floatNode: Represents a 1D scalar floating-point value. In generated WGSL, it maps to f32, and in GLSL, it maps to float. It holds a single continuous value and does not contain sub-components.
  • colorNode: Represents a multi-component vector, typically a 3D vector (vec3 in GLSL or vec3<f32> in WGSL) corresponding to red, green, and blue channels. While it behaves structurally like a vec3Node, it is specifically tagged within the TSL hierarchy to handle color-specific operations.

Color Space Awareness and Conversions

The primary structural distinction separating a colorNode from a standard vector or scalar node is how TSL handles color management:

  • Automatic Color Space Conversion: When a colorNode is instantiated using a Three.js Color object or a hex value, TSL flags the node for color management. During code generation, TSL automatically injects conversion routines (such as converting sRGB inputs into the renderer's working linear color space).
  • Direct Scalar Passthrough: A floatNode represents raw mathematical data. It undergoes no color space conversions regardless of the renderer's color management pipeline. It passes directly to the shader uniform buffer as a raw scalar.

Uniform Buffer Layout and JavaScript Representation

In the material definition on the JavaScript side, the nodes map to different native types and memory layouts in the uniform buffer:

  • floatNode Uniforms: Backed by a standard JavaScript number. In memory, it requires a single 4-byte float slot within a uniform buffer (subject to standard 16-byte alignment rules depending on surrounding data).
  • colorNode Uniforms: Backed by an instance of THREE.Color. When packed into a uniform buffer, it occupies three sequential 4-byte float slots (r, g, b), often aligned to 16 bytes inside standard uniform blocks.

Swizzling and Property Access

Due to their differing dimensions, TSL provides distinct property interfaces for each node type:

  • floatNode: Does not support channel swizzling directly because it has no vector components. However, it can be broadcast to higher dimensions by passing it into vector constructors, such as vec3(myFloatNode).
  • colorNode: Supports component accessors and swizzling. Developers can access individual channels using color-specific properties (.r, .g, .b) as well as traditional spatial coordinates (.x, .y, .z), or multi-channel swizzles like .rgb and .bgr.

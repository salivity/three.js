How Three.js Lensflare Uses Occlusion Queries

This article explores how the Three.js Lensflare add-on leverages WebGL hardware occlusion queries to accurately determine when a light source is hidden behind 3D geometry. By offloading visibility tests to the GPU rather than performing expensive CPU-side raycasting, the engine evaluates depth buffer interactions asynchronously. You will learn the technical mechanics behind this process, including proxy geometry rendering, query polling, and how the results dynamically scale flare opacity.

The Occlusion Challenge

In real-time 3D graphics, a lens flare should only be visible when the light source has a clear line of sight to the camera. Determining this visibility on the CPU using raycasting is computationally expensive, especially in scenes with complex meshes or animated models. Furthermore, CPU raycasting does not natively account for complex GPU states, such as depth testing, alpha-tested geometry, or displacement mapping.

To achieve pixel-accurate visibility testing without burdening the CPU, Three.js shifts this calculation to the graphics processor using hardware occlusion queries.

Setting Up the Occlusion Query

When WebGL 2.0 is active (or when using the EXT_disjoint_timer_query extension in WebGL 1.0), the GPU provides the ability to count how many visual samples pass the depth and stencil tests during a draw call.

The Lensflare implementation manages this through the WebGL API:

  1. Query Creation: The system generates a WebGL query object using gl.createQuery().
  2. Target Mode: The query is bound with the target gl.ANY_SAMPLES_PASSED or gl.ANY_SAMPLES_PASSED_CONSERVATIVE. The conservative variant allows the GPU to return a faster boolean-style confirmation of whether any fragment passed, prioritizing performance over precise fragment counts.

The Proxy Geometry Pass

Instead of testing the light source as an abstract mathematical point, the Lensflare add-on draws a miniature proxy mesh—typically a 16×16 pixel quad or a small bounding shape—positioned directly at the light's world coordinates.

The occlusion testing process follows these steps during the render loop:

  1. Scene Depth Pre-Pass: The main 3D scene is rendered normally, populating the depth buffer with the distance values of all opaque and transparent objects.
  2. Depth Masking: The renderer disables color writes (gl.colorMask(false, false, false, false)) and depth writes (gl.depthMask(false)). This ensures the proxy geometry remains completely invisible and does not alter the scene's existing depth values.
  3. Beginning the Query: The driver initiates the query with gl.beginQuery(...).
  4. Drawing the Proxy: The proxy geometry is drawn with depth testing enabled (gl.depthFunc(gl.LEQUAL)). The GPU tests the proxy fragments against the previously rendered scene depth buffer.
  5. Ending the Query: The call to gl.endQuery(...) instructs the GPU to tally how many fragments of the proxy successfully passed the depth test.

If geometry sits between the camera and the light, the proxy fragments fail the depth test. If the path is clear, some or all fragments pass.

Asynchronous Polling and Pipeline Management

Retrieving query results synchronously would cause a GPU pipeline stall (a CPU-GPU sync point), forcing the CPU to wait until the GPU finishes rendering the frame, which degrades framerates.

To prevent this bottleneck, the Lensflare add-on handles results asynchronously:

  • On subsequent frames, the script checks if the query result is available using gl.getQueryParameter(query, gl.QUERY_RESULT_AVAILABLE).
  • Once the GPU sets this flag to true, the code calls gl.getQueryParameter(query, gl.QUERY_RESULT).
  • Because the result is read one or two frames after the draw call occurred, the visibility check operates with a slight latency.

Updating Flare Visibility

Once the passed sample count is obtained, the add-on computes an occlusion ratio:

\[\text{Visibility} = \frac{\text{Samples Passed}}{\text{Total Expected Samples}}\]

If the result indicates the proxy was fully occluded, the visibility is set to zero. If partially occluded, such as when a light peeks around an edge, a fractional value is returned.

This visibility ratio is then used to modulate the opacity and scale of each flare element defined within the Lensflare instance. To mask the frame delay inherent in asynchronous polling, the system linearly interpolates (lerps) the flare’s opacity between frames. This results in a smooth transition as the light emerges from or disappears behind solid objects in the 3D environment.
